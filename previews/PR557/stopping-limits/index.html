Limits of the stopping tests

This page keeps its published links. The full material is now organized in Learn and Contracts.

See the current section.

What a cap says about stationarity

When a limit is already reached at a checkpoint, PGD, APG and CD skip a fresh ScaledKKT check. This includes a scheduled check at the iteration cap. In CD, the check is skipped at the pass cap or when the next sweep cannot fit the remaining visit budget. A skipped check is reported as :not_checked. If it was the only selected condition, the result reports reason = :limit and converged = false.

ObjectiveChange can still pass using the available checkpoint objectives. An APG stationarity check admitted before the cap can also pass when it uses the last permitted evaluation. See STOP-22, STOP-24 and CD-12 for the checkpoint rules.

Select stopping conditions in dense least-squares PGD

Use stopping to choose a condition and limits=MaxIterations(n) to cap the number of accepted updates. These keywords also apply to AccProxGradDescent on the supported dense least-squares route. AnyOf accepts the first passing condition. AllOf needs its conditions to pass at the same checkpoint. IterateChange and ObjectiveChange measure progress between accepted points. UserStop accepts a predicate over scalar checkpoint metadata. With NormL1 or ElasticNet, ScaledKKT(rtol=...) checks computed coordinatewise stationarity. The stopping contract specifies the comparison scales, option conflicts and checks available at the cap.

using ProximalBase, ProximalSolvers

X = [1.0 0.0; 0.0 2.0; 0.0 0.0]
y = [2.0, -2.0, 0.5]
x = zeros(2)
rule = AllOf(IterateChange(atol=1e-10, rtol=1e-7),
             ScaledKKT(rtol=1e-5))
r = solve!(x, LeastSquaresLoss(y, X), NormL1(0.1),
           ProximalGradientDescent(); stopping=rule, limits=MaxIterations(200))
termination(r)

termination(r).satisfied says whether the selected expression passed. r.converged is true when the winning branch includes a passing ScaledKKT. The result contract describes the stop reason, winning leaves, observations and counts. Omit both keywords to use the solver’s default stopping policy.

At the iteration cap, IterateChange and UserStop are marked :not_checked. In APG, an evaluated KKT check uses the gradient at the accepted point and includes its cost in the oracle counts.

Schedule stationarity checks in PGD and APG

Every(k, ScaledKKT(rtol=...)) makes the check eligible at the starting point and after every k accepted steps. This can save accepted-point gradient evaluations in APG. You can combine a scheduled check with other conditions through AnyOf or AllOf.

using ProximalBase, ProximalSolvers

x = [1.0]
f = LeastSquaresLoss([0.0], ones(1, 1))
r = solve!(x, f, NormL1(1.0), AccProxGradDescent(α=0.75, β=0.375);
           stopping=Every(2, ScaledKKT(rtol=0)), limits=MaxIterations(3))
@assert x == [0.0] && r.iterations == 2 && r.converged
termination(r)
(reason = :rule, satisfied = true, winning_branch = ((),), iteration = 2, limit = MaxIterations(3), limit_reached = false, observations = ((path = (), name = :ScaledKKT, evidence = :stationarity, status = :pass, value = true, threshold = true, scale = missing),), counts = (f_calls = 8, grad_calls = 4, g_calls = 4, prox_calls = 3, backtrack_steps = 3, rejected_trials = 1), evaluation_limits = (), reached_evaluation_limits = ())

An off-schedule check is reported as :not_checked. A scheduled check at a reached iteration cap is also :not_checked, including when the cap is a multiple of k. With MaxIterations(2) in the example above, APG returns the same point with reason = :limit and converged = false. Evaluation caps apply at each step. See STOP-25 for limit ties.

Cap the evaluations in dense least-squares PGD

Use a single call limit or a tuple to cap multiple kinds of work. MaxObjectiveEvaluations counts smooth loss values, and MaxGradientEvaluations counts full gradients. A fused evaluation uses one of each. MaxProximalEvaluations counts the penalty's proximal calls, including any trials the line search discards.

using ProximalBase, ProximalSolvers

x = zeros(1)
f = LeastSquaresLoss([1.0], ones(1, 1))
method = ProximalGradientDescent(ls=ProximalSolvers.LineSearches.BackTracking(α=1.0))
r = solve!(x, f, NormL1(0.0), method;
           limits=(MaxIterations(20), MaxObjectiveEvaluations(4)))
@assert x == [1.0] && r.iterations == 1
@assert termination(r).counts.f_calls == 4
@assert termination(r).reached_evaluation_limits == (MaxObjectiveEvaluations(4),)
termination(r)
(reason = :limit, satisfied = false, winning_branch = nothing, iteration = 1, limit = MaxIterations(20), limit_reached = true, observations = (), counts = (f_calls = 4, grad_calls = 2, g_calls = 3, prox_calls = 2, backtrack_steps = 1, rejected_trials = 1), evaluation_limits = (MaxObjectiveEvaluations(4),), reached_evaluation_limits = (MaxObjectiveEvaluations(4),))

The second trial uses the last smooth value. PGD returns the first accepted point because completing the second update needs one more smooth value as part of a fused gradient call. The report counts work on both trials. See STOP-23 for admission and RES-04 for the report fields.

Cap the evaluations in dense least-squares APG

AccProxGradDescent accepts the same hard call limits. A line search can reuse its last gradient for several proximal trials. If acceleration requires a restart, APG checks the remaining budget before evaluating the restart gradient.

using ProximalBase, ProximalSolvers

x = zeros(1)
f = LeastSquaresLoss([1.0], ones(1, 1))
r = solve!(x, f, NormL1(0.0), AccProxGradDescent(α=0.75, β=0.375);
           limits=(MaxGradientEvaluations(1), MaxProximalEvaluations(2)))
@assert x == [0.5] && r.iterations == 1
@assert termination(r).counts.grad_calls == 1
@assert termination(r).counts.prox_calls == 2
termination(r)
(reason = :limit, satisfied = false, winning_branch = nothing, iteration = 1, limit = MaxIterations(200), limit_reached = true, observations = (), counts = (f_calls = 4, grad_calls = 1, g_calls = 3, prox_calls = 2, backtrack_steps = 2, rejected_trials = 1), evaluation_limits = (MaxGradientEvaluations(1), MaxProximalEvaluations(2)), reached_evaluation_limits = (MaxGradientEvaluations(1), MaxProximalEvaluations(2)))

The search evaluates one gradient and takes two trials. It accepts the second and reports both caps. If you add a ScaledKKT rule, evaluating stationarity at the accepted point can require its own smooth value and gradient. See STOP-24 for when that work is allowed.

Select stopping conditions in scalar coordinate descent

For dense vector least-squares lasso with unweighted NormL1, turn momentum off and pass a rule, a pass budget, or both. A full sweep visits all coefficients. An active sweep revisits the active coordinates. Both count toward MaxPasses. ObjectiveChange compares consecutive full sweeps. UserStop can run after either kind of sweep before the cap.

using ProximalBase, ProximalSolvers

X = [1.0 0.0; 0.0 2.0; 0.0 0.0]
y = [2.0, -2.0, 0.5]
x = zeros(2)
r = solve!(x, LeastSquaresLoss(y, X), NormL1(0.5),
           CDSolver(order=:cyclic, momentum=false);
           stopping=ObjectiveChange(), limits=MaxPasses(20))
@assert x == [1.5, -0.875]
@assert termination(r).satisfied
@assert termination(r).counts.full_passes == 2
termination(r)
(reason = :rule, satisfied = true, winning_branch = ((),), iteration = 3, limit = MaxPasses(20), limit_reached = false, observations = ((path = (), name = :ObjectiveChange, evidence = :progress, status = :pass, value = true, threshold = true, scale = missing),), counts = (full_passes = 2, active_passes = 1, coordinate_visits = 6, objective_evaluations = 2, gradient_evaluations = 0), evaluation_limits = (), reached_evaluation_limits = ())

The orthogonal columns give the lasso solution [1.5, -0.875] on the first full sweep. The next full sweep has the same objective and satisfies the rule. Read termination(r).satisfied for progress and termination(r).counts for full passes, active passes, visits, and objective evaluations. CD-10 specifies these checkpoints.

To check stationarity instead, select ScaledKKT. It evaluates the full gradient at the completed coefficients after an eligible full sweep. On this example it can stop after the first sweep.

stationary = solve!(zeros(2), LeastSquaresLoss(y, X), NormL1(0.5),
                    CDSolver(order=:cyclic, momentum=false);
                    stopping=ScaledKKT(rtol=1e-6), limits=MaxPasses(20))
@assert stationary.minimizer == [1.5, -0.875]
@assert stationary.converged && stationary.passes == 1
@assert termination(stationary).counts.gradient_evaluations == 1
termination(stationary)
(reason = :rule, satisfied = true, winning_branch = ((),), iteration = 1, limit = MaxPasses(20), limit_reached = false, observations = ((path = (), name = :ScaledKKT, evidence = :stationarity, status = :pass, value = true, threshold = true, scale = missing),), counts = (full_passes = 1, active_passes = 0, coordinate_visits = 2, objective_evaluations = 1, gradient_evaluations = 1), evaluation_limits = (), reached_evaluation_limits = ())

A passing ScaledKKT in the winning branch sets converged=true. See CD-12 for the gradient count and checkpoint rules.

Add MaxCoordinateVisits(n) to cap visits across full and active sweeps. CD stops before a scheduled sweep that costs more than the visits left. Here a full sweep takes two visits.

budgeted = solve!(zeros(2), LeastSquaresLoss(y, X), NormL1(0.5),
                  CDSolver(order=:cyclic, momentum=false);
                  limits=(MaxPasses(20), MaxCoordinateVisits(3)))
@assert budgeted.passes == 1
@assert termination(budgeted).counts.coordinate_visits == 2
@assert termination(budgeted).reached_evaluation_limits == (MaxCoordinateVisits(3),)
termination(budgeted)
(reason = :limit, satisfied = false, winning_branch = nothing, iteration = 1, limit = MaxPasses(20), limit_reached = true, observations = (), counts = (full_passes = 1, active_passes = 0, coordinate_visits = 2, objective_evaluations = 1, gradient_evaluations = 0), evaluation_limits = (MaxCoordinateVisits(3),), reached_evaluation_limits = (MaxCoordinateVisits(3),))

The solver returns after the first full sweep with one visit left, since the next sweep also visits two coordinates. See CD-11 for admission.

Select stopping conditions in consensus ADMM

For a centered quadratic with an unweighted L1 penalty, use a fixed-penalty ADMMSolver and select either or both native residual tests. The solver checks them after a complete iteration. The thresholds come from the solver's abstol, abstol_dual and reltol settings.

using ProximalBase, ProximalSolvers

z = zeros(1)
f = SqrNormL2(1.0, [3.0])
g = NormL1(1.0)
r = solve!(z, f, g, ADMMSolver(abstol=1e-8, reltol=0.0);
           stopping=AllOf(PrimalResidual(), DualResidual()), limits=MaxIterations(100))
@assert isapprox(z, [2.0]; atol=1e-7, rtol=0.0)
@assert r.converged
termination(r)
(reason = :rule, satisfied = true, winning_branch = ((1,), (2,)), iteration = 29, limit = MaxIterations(100), limit_reached = false, observations = ((path = (1,), name = :PrimalResidual, evidence = :residual, status = :pass, value = 0.0, threshold = 1.0e-8, scale = missing), (path = (2,), name = :DualResidual, evidence = :residual, status = :pass, value = 5.587935447692871e-9, threshold = 1.0e-8, scale = missing)), counts = (f_calls = 1, g_calls = 1, prox_calls = 58), evaluation_limits = (), reached_evaluation_limits = ())

AllOf requires both tests to pass. The report gives the residuals and thresholds for the evaluated leaves, and records any tie with a limit. For a warm start, keep the returned consensus variable, scaled dual r.u and penalty r.ρ together. See ADM-06 for when the tests run and RES-06 for the result fields.

Use limits=(MaxIterations(100), MaxProximalEvaluations(3)) to set both caps. A complete ADMM iteration takes two proximal calls. A cap of three therefore permits one iteration, and the report lists the reached MaxProximalEvaluations(3) with counts.prox_calls == 2. A residual rule can still pass on that iteration. See ADM-07.

z_budget = zeros(1)
cap = MaxProximalEvaluations(3)
limited = solve!(z_budget, f, g, ADMMSolver();
                 limits=(MaxIterations(100), cap))
@assert z_budget == [0.5] && limited.u == [1.0]
@assert termination(limited).counts.prox_calls == 2
@assert termination(limited).reached_evaluation_limits == (cap,)
termination(limited)
(reason = :limit, satisfied = false, winning_branch = nothing, iteration = 1, limit = MaxIterations(100), limit_reached = true, observations = (), counts = (f_calls = 1, g_calls = 1, prox_calls = 2), evaluation_limits = (MaxProximalEvaluations(3),), reached_evaluation_limits = (MaxProximalEvaluations(3),))

The criterion and a certificate

See the current section. For PGD and APG on least squares with a dense vector response and NormL1 or ElasticNet, a kept stop records that each coordinate's computed score passed the rule: below its computed threshold, or at most 0 at an exact zero scale, where no threshold is formed. In exact arithmetic the same comparison would bound the decrease available from each coordinate of the model that the check scores, under the conditions of STOP-21 (that model is the objective of the solve when their coefficients agree); neither bounds the error of the objective or the coefficients in general, and an exact or near-exact fit can return converged = false. The matrix-response lasso of IN-10 keeps the λmax-based check of STOP-03. For square-root lasso, a bounded fallback can certify an uncertified stopped point or return a point with a proved lower objective; recovery at exact fits is not guaranteed. See the bounded recovery rule. On the ℓ1-ball route of PGD and APG, converged means that the full check passed at the returned point, which can lie outside the ball and still pass the computed cap decision (IN-12).
