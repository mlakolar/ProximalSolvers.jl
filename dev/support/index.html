Supported problems

This page describes the current GitHub development master branch, not the wider feature set in historical releases.

What works today?

The supported objective is a lasso:

\[\min_\beta\quad \frac{s}{2}\|y-X\beta\|_2^2+\lambda\|\beta\|_1,\]

where s=1 for raw LeastSquaresLoss or s=1/n for the usual normalized convention.

InputSupported
Design matrix XNonempty, finite, dense Matrix{Float32} or Matrix{Float64}
Response yFinite vector with the same element type and length(y) == size(X,1)
Coefficients betaSame-type dense vector for CD, PGD or APG; alternatively, one-dimensional ProximalBase SparseIterate for CD only
LossLeastSquaresLoss or one finite positive scalar multiple of it
PenaltyUnweighted NormL1(lambda) with nonnegative finite lambda
SolversCDSolver, ProximalGradientDescent, AccProxGradDescent (APG also needs max(n, p) + 4 < 1/(4 eps(T)) and n p + 3 < 1/(4 eps(Float64)))

The three numerical arrays use one common T (Float32 or Float64); mixed-element-type X, y and coefficient arrays are not supported. The finite loss scale and penalty level must be representable in T without overflow or rounding a nonzero scalar to zero. They may be supplied in a different scalar type, including a representable Float64 literal in a Float32 problem. After that check, CD, PGD and APG use the loss scale as supplied, combined with T by Julia's promotion (CD converts a scale to T when that promotion is not a concrete floating-point type): a Float64 scale in a Float32 problem keeps its Float64 value, also where that value is subnormal in Float32. The arrays and the coefficients stay in T, so this does not imply mixed-precision array support or a guarantee about every intermediate arithmetic type. A BigFloat, BigInt or Rational{BigInt} loss scale makes the scalar arithmetic of CD that involves it (the step coefficient, the products of the loss scale in the two stopping scales, and the reported objective's product) BigFloat, at the precision current when the solve runs; the square roots of the stopping scales on their normal-range branch are formed in T. It allocates and is slow, and is not a fast path.

The data must not be modified while a solve is running. The coefficient vector (or the supported CD SparseIterate) is mutated in place, so do not alias it to X or y. To retain a result, save copy(beta). See Numerical behavior for numerical recovery limits, solver stopping and diagnostics.

For an executable complete example, see Getting started. For using sparse coefficients, see the sparsity tutorial. The design matrix still must be dense, even when the coefficients use SparseIterate.

What is not supported yet?

The current development core intentionally excludes the following:

FeatureCurrent status
Sparse design matrices; sparse or view-based dense coefficientsDeferred
Generalized losses, matrix responses, intercepts/offsetsDeferred
Weighted or group penalties, generalized penalty combinationsDeferred
Penalty paths, screening and dual-gap certificatesDeferred
ADMM, Newton, monotone or active-set accelerated gradient, primal-dual, SLOPE, graphical modelsDeferred
Generic workspaces, refitting, reweightingDeferred
PGD or APG with SparseIterate coefficientsDeferred
CD anderson>0, gaptol>0, gapsafe=trueRejected; not implemented
ProximalOptions(gaptol>0)Rejected when the options are constructed; not implemented
PGD normalized=true, debias>0, preconditioner != :noneRejected; not implemented
APG preconditioner != :noneRejected; not implemented

Some rejected keywords remain accepted by constructors, at their default values only, to provide informative errors and compatibility with historical signatures; the solvers and options do not store them. Do not interpret their presence as available functionality. The reported gap=NaN and CD's kkt_checks=0 are placeholders, not computed certificates.

About previous versions

The registered package and historical legacy/full branch may expose features that this development branch intentionally does not. These are different development stages; this documentation does not provide a migration procedure for every historical algorithm. Consult Getting started for source installation.

See Numerical behavior for stopping and precision. Detailed implementation, failure transaction and internal algorithm contracts are preserved under Contributor implementation notes.
