Contracts for the current solver core

Read this layer when implementing, reviewing or diagnosing solver behavior. Each numerical rule has one full statement with a stable clause ID. The Learn chapters develop the mathematics, and the Use pages explain how to call the package.

Reading order

Start with the routine's contract, then read inputs, working precision and results and failures. A mathematical identity does not by itself specify the computation: the clause also states accepted data, arithmetic, refusal timing and mutation boundaries.

Clause schema

A numbered clause contains Statement, Applies to and Sources. Code identifies the implementation, and Tests points to existing checks or explains why a separate test is unnecessary. Algorithm, proof and known-limit subsections may expand a clause. Sources refer to immutable baseline blocks in docs/migration/baseline.json; the matching row of docs/migration/ledger.csv records where each original block went.

A source citation records provenance. It does not certify that two formulations are equivalent. The migration initially preserved conflicting wording under Unreconciled headings. The four historical specification conflicts were resolved in issue #416; their original quotations and permanent anchors remain under Retired historical wording, with links to the authoritative clauses. Evidence pages retain measured outcomes, platforms, dates and revisions; those observations are not new solver guarantees.

Clause IDs are permanent. When a clause is replaced, keep its heading, mark it Retired, and link explicitly to the replacement. New clauses receive new IDs.

λ, lambdaPenalty level; λ₁, λ₂ for elastic net

Retained proofs and excerpts may call the loss scale α or α_f, or use x for the coefficients. Their local notation is stated where it matters. Public constructor keywords and stored fields retain their API spelling.

Historical records

The repository's archived contracts are historical evidence. They describe a wider implementation of ADMM as well as deferred algorithms including QUIC and SLOPE. Use the clauses here and the current support matrix for the implemented surface. The archive is intentionally unchanged. History records earlier branches and dependency provenance; architecture describes the source layout.

Internal glossary

Owner: An internal name for the caller's mutable coefficient storage. In beginner-facing pages, we call it the coefficient vector or coefficient storage.

Sentinel: A placeholder value, such as kkt_checks=0, or gap=NaN where no certificate was computed or none passed, indicating that a diagnostic is not available.

TFOCS: Templates for First-Order Conic Solvers. A historical first-order optimization framework; the name appears in descriptions of PGD's inherited backtracking behavior. It is not a separate solver offered by this minimal version.

FASTA: Fast Adaptive Shrinkage/Thresholding Algorithm. Historical terminology for a first-order algorithm and a residual-style stopping test. Its appearance in implementation notes does not mean this package exposes a separate FASTA solver.

IHT: Iterative hard thresholding, a method for imposing a fixed sparsity budget by retaining selected entries. normalized=true IHT-style behavior is not supported by the current PGD constructor.

C0: An internal project label for the frozen baseline characterization and regression tests used during the minimal-core rebuild. It is not a solver option or a user-facing algorithm.
