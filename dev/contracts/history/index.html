Contract and implementation history

These notes preserve development history and the provenance of the documented behavior. They do not turn historical measurements or platform runs into current performance or support guarantees.

HIST-01 Reduced development core and historical branches

Statement.

The supported core is a breaking support reduction. Version selection, registration and a public release remain separate decisions; existing releases are untouched. Protected archive references preserve the complete snapshot and legacy/full remains the historical working branch. Restore capabilities selectively rather than merging that branch wholesale.

Registered versions and legacy/full may expose features intentionally absent from this development branch. They represent different development stages, and this documentation does not give a migration procedure for every historical algorithm. Getting started describes source installation; DEF-01 lists deferred capabilities. Numerical, stopping and internal contracts are now collected under working precision, results and architecture.

Applies to. Development/release history and the relation of the reduced core to older branches.

Code. Repository branch/archive policy; current public dispatch in src/solve.jl.

Tests. This is release and provenance history, not a new claim that historical algorithms pass current tests.

HIST-02 Least-squares oracle and scalar-scale alignment

Statement.

The homogeneous numerical policy was aligned with ProximalBase PR #857. Failure atomicity was retained. The accepted loss-scale types narrowed when loss values and gradients moved to ProximalBase's least-squares oracles (#307).

Before that narrowing, a BigFloat, BigInt or Rational{BigInt} scale made CD's scalar arithmetic BigFloat; an Int, Rational{Int}, Irrational, Bool or Float16 scale was used there as T(s). These historical cases do not expand the current scale contract in IN-02.

CD coordinate steps and stopping arithmetic stayed as before where the loss scale promotes to T. For a wider accepted loss scale, they use the supplied scale (#295). The loss part of the reported objective is now ProximalBase's reduction, which differs from the former reduction in T (#307). Exceptional oracle recovery can evaluate values for which the old direct sum of squares overflowed, subject to the current range limits. CD formerly refused a finished solve when that sum overflowed; PGD/APG formerly formed the sum in T without this oracle recovery.

Applies to. Historical rationale for current input types, scale arithmetic and objective oracles.

Code. src/solve.jl: scale gate; src/cd/leastsquares.jl; src/solvers/image_models.jl; the pinned ProximalBase oracles.

Tests. Current behavior is covered by the tests cited in IN-02, FP-02 and CD-09; this note preserves the previous behavior without reinstating it.

Sources. docs/src/numerics.md:L743, docs/src/numerics.md:L812, docs/src/numerics.md:L827, docs/src/developer/implementation-notes.md:L179.

HIST-03 Dependency pin and paired-diagnostic provenance

Statement.

At the migration baseline, the exact ProximalBase pin is 7d5d1e006b02814fb28f8cfb5eca20a05d73ee9e. The private SparseIterate contract is unchanged and PR #237's group/workspace migration is not imported.

ProximalBase's linked /dev/ documentation follows its evolving master, while ProximalSolvers uses a fixed dependency commit, so details can differ. Consult the exact pinned source and installation guide for compatibility.

The preserved analysis policy runs isolated exact-source paired diagnostics against ProximalBase A e8a45a8a6ffe2a6f92d83c4c77d62a9b7631e291 and frozen ProximalSolvers 64930401cfc0451e886728d916263c4dab2baf36, for CD and PGD only, including when package tests are not selected or are reused. Loaded paths, clean Git HEADs and source digests are checked; version strings never skip probes. C0 and the provenance audit describe the independent full-suite mathematical and behavioral tests. These identifiers and requirements are provenance for that analysis; the documentation migration does not change dependency pins or claim a new diagnostic run.

Applies to. Pinned-source and paired-analysis provenance retained from the implementation notes.

HIST-05 Float32 support-note wording before nonnegative lasso

Statement.

The migration baseline's support note (a) listed weighted lasso as its exception to tests that did not require a successful convergence flag. The original wording is retained here as historical testing context:

  • (a) ProximalGradientDescent and AccProxGradDescent accept Float32 data, and the tests check the returned point against BigFloat or Float64 references with Float32-sized tolerances, and (except for the weighted lasso, see (f)) do not require converged = true, because a Float32 solve can end without it: with ftol = 0, ProximalGradientDescent can stop at numerical stagnation with stagnated = true and converged = false, and with the default options a Float32 solve can end on the objective-increase exit with converged = false. Assess the returned point with an independent residual; see Numerical behavior.

Upstream commit fd45a4274222e7cfe8f329c1dacd41ec26bfc2c8 (PR #413) adds test/nonnegative_lasso.jl, which explicitly requires converged in its case with an inactive coefficient and a positive loss derivative, for both element types. The current support note (a) therefore also names selected nonnegative-lasso checks. This adds test coverage; it does not turn all Float32 stopping flags into accuracy certificates.

Applies to. Historical support-note wording and the subsequent nonnegative-lasso test addition.

Code. Upstream fd45a4274222e7cfe8f329c1dacd41ec26bfc2c8: test/nonnegative_lasso.jl.

Tests. The upstream nonnegative-lasso test requires feasibility and independent objective/KKT checks, with the explicit convergence assertion described above.
