Results and troubleshooting

solve! writes the coefficients into the array you pass to it, and returns a result describing the last point and the stopping process.

Read a result

using ProximalBase, ProximalSolvers
X = [1.0 0.0; 0.0 2.0; 0.0 0.0]
y = [2.0, -2.0, 0.5]
f = (1 / length(y)) * LeastSquaresLoss(y, X)
penalty = NormL1(0.1)
beta = zeros(2)
r = solve!(beta, f, penalty,
           CDSolver(order=:cyclic, momentum=false))
@assert r.minimizer === beta
@assert isapprox(beta, [1.7, -0.925]; atol=1e-7)
(; coefficients=beta, objective=r.minimum, passes=r.passes,
   converged=r.converged)
(coefficients = [1.7, -0.925], objective = 0.3229166666666667, passes = 3, converged = true)

Every solver reports minimizer, minimum and converged. Coordinate descent also provides passes, maxchange, and tolerance. PGD and APG provide iterations, more detailed stopping residuals and an optional iteration trace. These differ because the current package retains two algorithm-specific result types.

Warning: for PGD and APG, converged=true means that a stopping test proposed a stop and that the computed KKT residual ‖G‖∞ at the returned point is below max(gradtol, 64eps(T)) * max(λ, λmax), with λmax = α‖Xᵀy‖∞ and λ the ℓ1 level of the penalty (λ of NormL1(λ), the largest coefficient T(λ) * maximum(w) of NormL1(λ, w), λ1 of ElasticNet(λ1, λ2)): a working-precision value. converged = true guarantees only that the computed, normalized KKT residual ‖G‖∞ / max(λ, λmax) is below max(gradtol, 64eps(T)) (the threshold is formed in T, where it can round or overflow; see the stationarity check). It is not an exact-arithmetic certificate, not a bound on the distance to a minimizer, and does not guarantee coefficient accuracy on ill-conditioned designs (see the stationarity check). For CD with least squares or the group lasso it means that a stopping rule was satisfied. Neither certifies the output as optimal. For the lasso, use the separate numerical KKT check. For CD with the square-root loss, converged=true means that a duality certificate proved (P − P*)/P* ≤ 1e-4, and gap holds the proved bound (see CDSolver). Otherwise a result's gap=NaN and CD's kkt_checks=0 are placeholders: neither is a computed certificate.

For PGD and APG with a NormLinf penalty, converged=true means that a stopping test proposed a stop and that the generic proximal-gradient check passed: a working-precision indication, not a certificate.

Avoid accidentally overwriting results

saved_coefficients = copy(beta)
new_result = solve!(beta, f, NormL1(1.0),
                    CDSolver(order=:cyclic, momentum=false))
@assert isapprox(saved_coefficients, [1.7, -0.925]; atol=1e-7)
@assert isapprox(beta, [0.0, -0.25]; atol=1e-7)
(; saved_coefficients, new_coefficients=beta)
(saved_coefficients = [1.7, -0.925], new_coefficients = [0.0, -0.25])

The old r.minimizer points to the same beta that the second solve overwrote. Save a copy when keeping past fits.

What PGD's output labels mean

The result display's |g(x)| refers to an internal gradient/proximal stopping residual, not the value of your penalty object, even if you named that object g. Likewise, the displayed |x - x'| abbreviates a stopping diagnostic; see the API documentation for precise definitions. PGD can propose a stop when any of its stopping criteria is met, and the stop counts only if the computed KKT residual ‖G‖∞ is below max(gradtol, 64eps(T)) * max(λ, λmax); gradtol below 64eps(T) is not resolved by that check. See Numerical behavior.

Trace fields such as dxx describe relative iterate changes, and backtrack_steps counts line-search trials. These are solver diagnostics, not changes to the statistical model.

Convergence flag is falseInspect the solver's iteration/pass limit; check the KKT residual
gap is NaNGap certification is implemented only for the square-root lasso with CD; there, NaN means that the run stopped without a certificate
Square-root lasso: converged = false with a warning about a missing duality certificateThe certificate did not pass, for example at an exact fit (y = X*beta), where coordinate descent can stop at a coordinatewise minimum that is not a minimum; see CDSolver and an example
Float32 precision looks poorStart with native Float32 inputs/scales, check the KKT residual; Float32 has lower precision
Coefficients appear to change unexpectedlysolve! mutates the supplied coefficients; copy them to save the old solution

A SparseIterate stores active coordinate values. With CD, the caller's object is updated only after a completed finite run. The active-coordinate list may change: re-read activecoordinates and activevalues after solving rather than retaining old views. See Supported problems.
