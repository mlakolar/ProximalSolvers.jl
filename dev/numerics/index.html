Numerical behavior

This page explains what a successful solve does and does not promise. You can start using the package without understanding its internal algorithm code.

What does converged mean?

  • Coordinate descent (CD): the change during a full pass has fallen below the effective tol. With relative=true this threshold is scaled by a response-dependent quantity; the reported effective tolerance can differ from the value passed to the constructor.
  • Proximal gradient descent (PGD): the algorithm applies multiple stopping tests for relative coefficient change, objective change and a gradient/proximal residual. These combine by OR: passing one can stop the algorithm, even if the others remain large. ftol = 0 switches the objective-change test off (see Strict accuracy).
  • Accelerated proximal gradient (APG): the same three tests and the same objective-increase stop as PGD. Its gradient/proximal residual is L ‖x - y‖∞, measured from the extrapolated point y rather than from the previous iterate, so it is a stopping quantity, not a KKT residual at x.

Neither converged=true is a certificate of mathematical optimality. On the small tutorial examples, default PGD typically produces only about 3–4 correct digits even if it reports converged=true. This is not a bound or expected accuracy on arbitrary problems. Tighten tolerances for results you intend to report, then compute the independent KKT residual. The Concepts and Getting started pages display that residual next to the default-PGD convergence flag. PGD's printed |g(x)| label is an internal stopping residual, not the value of the user's L1 penalty.

PGD stops when the computed objective increases

With the default allow_f_increases=false in ProximalOptions, PGD has one more exit, which is not a convergence test: it stops at the first iteration whose computed objective F = f(x) + g(x), evaluated in the working precision, is larger than the previous iteration's F'. Such a stop does not mean the solve converged.

At the iteration where PGD stops, for whatever reason, the result's flags are evaluated as follows:

FieldValue at that iteration
x_convergednorm(x - x') < xtol * max(norm(x), 1); with ftol = 0, false when x == x' elementwise
f_convergedwith ftol > 0: abs(F - F') / (abs(F) + ftol) < ftol, or abs(F - F') < eps(abs(F) + abs(F')) (this form holds when F == F' and the sum is finite, and in the ordinary range, where F and F' are normal floating-point numbers and the sum is finite, it is about two units in the last place of F); with ftol = 0: false
grad_convergedthe gradient/proximal residual test with gradtol holds; with ftol = 0, false when x == x' elementwise
convergedat least one of x_converged, f_converged and grad_converged
f_increasedF > F'
iteration_convergediterations == maxiter

So an objective-increase stop reports f_increased=true together with converged=false, unless one of the three tests also held at that iteration. Two other combinations are possible and not contradictory:

  • With ftol > 0, in the ordinary range (F and F' normal floating-point numbers, abs(F) + abs(F') finite), an increase smaller than about two units in the last place of F passes the objective test, so the result reports converged=true and f_increased=true. With ftol = 0 the objective test is off, so an increase of any size reports converged=false unless the x or the gradient test held.
  • A test that succeeds at the last allowed iteration reports converged=true and iteration_converged=true. An objective-increase stop at that iteration also has iteration_converged=true.

With allow_f_increases=true this exit is removed: the solve continues until a test holds or a limit is reached, and f_increased only reports the comparison at the last iteration.

Why rounding triggers it. For the supported least-squares lasso, with the backtracking line search's default Lexact = Inf, an accepted step does not increase the objective in exact arithmetic. A computed increase comes from floating-point rounding. Near a minimizer, the true change in F per step becomes smaller than the rounding error of evaluating F in the working precision (which depends on the data; on a small test problem of this package, a first-order bound is about 16 eps(T) relative), so the sign of the computed change is decided by rounding. At strict tolerances, whether a solve that has reached the neighborhood of a minimizer ends with converged=true or with an objective-increase stop can therefore depend on the last bits of the trajectory rather than on the accuracy of the point. Those bits can change with the starting point, the CPU and its vector width, the BLAS kernel, and how the code is compiled (for example, with coverage instrumentation). It matters mainly for tolerances near or beyond the working precision, and the package's tests see it most often with Float32. In both directions, assess the returned point with the independent KKT residual, not with converged alone.

Strict accuracy

With ftol > 0, including the default 1e-6, the objective-change test also holds when two successive computed objectives are equal or, in the ordinary range (both normal floating-point numbers, abs(F) + abs(F') finite), differ by about two units in the last place. That can happen well before the point is accurate to the working precision. ProximalOptions(ftol = 0) switches the objective-change test off for ProximalGradientDescent and AccProxGradDescent: f_converged is false at every iteration. The objective-increase stop and the iteration limit are unchanged. So are the x and gradient tests, except that under ftol = 0 an iteration whose accepted iterate equals the previous one elementwise sets neither x_converged nor grad_converged (see "An exact stall" below). ftol must be finite and nonnegative; a positive ftol that rounds to 0 in Float64 is refused, so that a tiny positive value does not silently switch the test off.

This combination is a test configuration, not a general recipe:

ProximalOptions(maxiter = 20_000, ftol = 0, allow_f_increases = true,
                xtol = 1e-300, gradtol = 1e-11)

On the package's benchmark cases (Float64 PGD and APG, Float32 APG, with 10 input draws each, on Julia 1.10 and 1.13 and two CPU models) it met the independently computed targets of a relative duality gap of 1e-8 in Float64 and 1e-5 in Float32. It is not a guarantee of accuracy on other problems, and converged=true is still not a certificate: check the returned point independently, for example with the bound below. Float32 PGD did not meet its target in every draw with this configuration. In those probes (with maxiter = 2000), all 100 Float32 PGD solves ran to maxiter with converged=false, and the iterate was unchanged in 309 to 1992 of their 2000 iterations.

  • allow_f_increases = true. With the objective test off, a computed increase of F still ends the solve under the default allow_f_increases=false, and reports converged=false unless the x or gradient test held. Near a minimizer such increases can be at the level of rounding (see above). In the benchmark probes, switching off the objective tests alone ended most solves at an increase, and the configuration above, which met the targets in those probes, enables increases.
  • xtol is not an accuracy criterion for PGD. PGD's step is scaled by 1/L, where L is the inverse step size, so the test norm(x - x') < xtol * max(norm(x), 1) bounds the proximal-gradient residual by about L * xtol * max(norm(x), 1), which depends on L, on the scale of x and on the penalty level λ, not on an accuracy target. In the benchmark probes with xtol = 1e-14, one Float64 PGD draw (on Julia 1.10) missed the target, and it ended on the x test. xtol = 1e-300 lets that test hold only for steps of norm below 1e-300 * max(norm(x), 1), which still includes a nonzero step that small (for example x = [1e-310] after x_previous = [0.0]). In the benchmark probes with these tolerances, all Float64 solves ended on the gradient test.
  • An exact stall under ftol = 0. An iteration whose accepted iterate equals the previous one elementwise (by value) is no progress, not convergence: it sets neither x_converged nor grad_converged, and the solve continues, subject to the other tests, the limits and, with allow_f_increases=false, the objective-increase stop. With ftol > 0 such an iteration passes the x test. A stall can end when the step size 1/L or, for APG, the extrapolated point changes from one iteration to the next; they need not change (for example with a zero step or α = 1). A solve that stays at an unchanged iterate until maxiter ends with converged=false and iteration_converged=true; that reports no progress, not that the point is wrong (for x = 0 with a penalty level at or above norm(∇f(0), Inf), the point is the solution). For AccProxGradDescent, an extrapolated point y equal to x while x differs from the previous iterate is not a stall: its residual L * maximum(abs, x - y) is 0, so the gradient test holds when gradtol > 0.

A check of a lasso solution. Let f(x) = s‖y - Xx‖²/2 with s > 0 and g(x) = λ‖x‖₁ with λ > 0 (an unweighted NormL1), let F = f + g, and let G be the element of ∇f(x) + λ ∂‖x‖₁ of smallest infinity norm, which is the independent KKT residual. Put k = norm(G, Inf) / λ. With the dual point θ = κ s (y - Xx), where κ = min(1, λ / norm(∇f(x), Inf)) and κ = 1 when ∇f(x) = 0, and D(θ) = ⟨θ, y⟩ - ‖θ‖²/(2s), the relative duality gap satisfies

\[\frac{F(x) - D(\theta)}{F(x)} \le 2k + k^2\]

in exact arithmetic, for s > 0, λ > 0 and F(x) > 0. This follows from F(x) - D(θ) = (1-κ)² f(x) + (1-κ) λ‖x‖₁ + κ⟨G, x⟩, 1 - κ ≤ k and F ≥ max(f, λ‖x‖₁). Evaluating k in Float64 from the returned x is an independent numerical check, not a rigorous floating-point certificate: the rounding errors of that evaluation are not bounded here.

Working precision: Float32 and Float64

A supported solve uses a single floating-point working type T = Float32 or T = Float64 for the design matrix X, response vector y, and coefficient iterate. CDSolver accepts either a dense Vector{T} or a one-dimensional SparseIterate of T; ProximalGradientDescent and AccProxGradDescent accept only a dense Vector{T}. Mixed-precision arrays, such as Float32 coefficients with a Float64 design, are rejected. This is stricter than ProximalBase function dispatch, which may permit some heterogeneous calls without guaranteeing their numerical behavior.

Scalar-parameter exception. The loss scale in Scaled(LeastSquaresLoss(...), s) and the NormL1 penalty level lambda may be finite real scalars of a different type, including a Float64 literal for a Float32 solve. The solver checks that they are representable in T without overflow or loss of a nonzero parameter to zero. This convenience does not enable a general mixed-precision model or guarantee that every intermediate operation uses T. Prefer explicit native scalars:

T = Float32
s = one(T) / T(n)
lambda = T(0.1)
f = s * LeastSquaresLoss(y, X)
g = NormL1(lambda)

All supplied X, y and coefficient entries must be finite. Finite inputs do not guarantee finite intermediate arithmetic. The ProximalBase mathematical kernels use selective overflow/underflow recovery for some representable results, but ProximalSolvers does not promise end-to-end recovery of every failed matrix product, curvature, step or objective. Unrecoverable numerical failures are handled as described below; a successful kernel recovery does not imply the solver can continue in every extreme-range case.

Float32 has less precision and may stagnate earlier than Float64. Some solver tolerances, residual reports and other scalar diagnostics are stored as Float64 even when the iterate is Float32; this is bookkeeping, not higher-precision optimization or an accuracy certificate. In particular, a tolerance tighter than the working precision does not guarantee corresponding coefficient accuracy. Assess the returned result with an independent KKT residual, rather than relying only on converged.

Results and failures

  • CD on dense coefficients calculates on private storage, avoiding a partially written dense result if a numerical failure occurs.
  • CD on a SparseIterate uses a private copy and commits the final set of active coordinates only after finite completion. This means the original coefficient storage is unchanged if the numerical solve fails. A pass can remove zeros from the active list and change the order of stored coordinates. The RNG can still advance.
  • PGD uses in-place dense arrays, and restores the last accepted iterate if a numerical step fails. Its counters and other internals are not transactional.
  • APG does the same. Its backtracking raises an error, after which the last accepted iterate is restored, when the next curvature estimate L/β is not a finite increase; a trial whose objective is not finite is never accepted. An extrapolated point whose objective or gradient is not finite restarts the momentum when the step uses momentum; without momentum the step fails, with the same rollback. Its line search accepts a step only when the least-squares bound √α ‖X(x - y)‖ ≤ (1 + 4eps) √L ‖x - y‖ is certified by conservative floating-point error bounds for the stored x and y, so it does not subtract nearly equal objective values and does not accept a step whose bound check is dominated by rounding. It first uses the difference of the cached images X x and X y, whose error is bounded through ‖X‖_F and the iterate norms; when that bound leaves the decision open it computes X(x - y) afresh, one extra matrix-vector product whose error bound is a relative term proportional to the step plus an absolute underflow term, and rejects a step that is still undecided. The norms and the bound arithmetic are carried as significand and binary exponent, so they do not overflow or round to subnormal values in T; the native products and their underflow enter only through the bounds. A curvature above floatmax(T) is never certified, so backtracking then ends in its error with rollback. These bounds assume IEEE arithmetic with gradual underflow and a matrix-vector product evaluated as dot products; the native products and the extrapolation are computed in T and enter only through the bounds. The extra product is needed more often in Float32, where the bounds are wider relative to small late steps; for data deep in the subnormal range, where the underflow terms can dominate the bounds, a step may need L far above the curvature, or the solve may fail with rollback. APG also requires max(n, p) + 4 < 1/(4 eps(T)) and n p + 3 < 1/(4 eps(Float64)); larger problems are refused before x is modified.
  • Reaching a pass or iteration limit is not convergence. CD can return a finite nonconverged solution with a warning.

Gap certificates are not implemented: gap=NaN is a placeholder. For more precise treatment of exceptional arithmetic, compaction, momentum, callbacks and test provenance, consult the technical contract notes.
