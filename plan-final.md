### What reading the code showed (beyond the issue's inventory)

- **Two more call sites.** `src/utils.jl:145` `_gradient_at_x!(::AccProxGradDescentState)` calls `_image_value_and_gradient!` (APG's ∇f(x) for the stationarity check), reached from `_stationary!(state, g, options)` ← `convergence_assessment(state, f, g, options)`. `src/utils.jl:130` `_lambda_max!` forms `α‖Xᵀy‖∞` once per solve from the model; it is not a loss value and stays.
- **Passing `f`.** Every PGD/APG function that evaluates the loss already receives `f` and is already compiled per loss type. `_stationary!`, `_gradient_at_x!` and `_value!` gain an `f` argument; `f` is not stored in `_LSImage` or `LSModel`.
- **Raw scale `true` → `one(T)`.** `_LSImage` built from `leastsquares_data` holds `one(T)` for raw LS instead of `true`. Effects independent of the oracles: the raw path no longer multiplies the gradient by `true`; `_root_scale(T, true)` currently takes the 256-bit BigFloat path at each raw APG `initial_state`, and `one(T)` takes the IEEE path (same value, no allocation); and the raw Float64 PGD/APG state types become the same as the precompiled scaled-Float64 ones. All three affect first-call latency and bytes, and are reported separately from the oracle effect.
- **Behaviour that changes because PB computes the value** (expected, reported, not hidden):
  1. Values PS overflowed or underflowed are now recovered: CD's final objective (R3 of #277), PGD/APG values with a small scale and a large residual, and the starts that `_check_start` used to refuse. Tests that flip: `core_contracts.jl:12-15`, `cd_numerics.jl:924-946` (R3 overflow: the solve no longer fails; the reported value is checked against a 256-bit reference), `cd_numerics.jl:948-960` (R3 underflow: `=== zero(T)` becomes PB's documented allowance of `2 nextfloat(zero(T))`). Tests that stay refusals (value still non-finite): `sparse_cd.jl:262,346,355`, `core_contracts.jl:19`, `cd_numerics.jl:799`. Docs: `numerics.md:403-408` and the PGD/APG statements.
  2. The value oracle recovers an overflowing `z - Y`, while the combined oracle gives a non-finite value and gradient there (PB's documented contract). In PGD a trial can then be accepted on a finite value, after which the gradient refresh writes a non-finite gradient; before, both were `Inf` and the trial was rejected. The outcome (backtracking, error with rollback, or another stop) is measured in the sweep and documented. No PS-side recovery is added.
  3. Last bits on the ordinary path: the old combined path used Base `sum(abs2, d)`; PB uses one `@simd` loop up to 2¹⁷ entries and pairwise summation above. This can move APG restarts, `f_increased`, the `ftol` exact-stall test and PGD's `backtrack_simple`. Tests with exact counts and snapshots to watch: `accelerated_pgd.jl:834-857`, `core_regressions.jl:693,712,845-859`, `stopping_scale.jl:151,178,264`, `minimal_core_characterization.jl:392-437`. A count that changes is accepted only with the solution's independent certificate unchanged in quality, explained in the round comment.
  4. Integer scales: PB scales the value and the gradient by `Float64(α)`, while CD's steps and stopping (`_scale_type`), `_lambda_max!` and `_step_curvature` use `T(α)` for an integer. Under the D1 rule below an integer scale is accepted only when `T(α) == α`, so all of these use the same real number; an integer that `T` does not hold (`Int(2^24 + 1)` with Float32 data) is refused instead of being rounded in CD.
- **Test call sites of the changed internal signatures**: `PS._value!` (`core_regressions.jl:244,258,486`), `PS._stationary!` (`stopping_scale.jl:252,290,297`), `PS.loss_value` (`cd_numerics.jl:472,487,488,495,506`, `core_regressions.jl:59`), and the `CDModel` fallback `loss_value` (`src/cd/models.jl:8`) are updated with the signatures.

### D1, ruled by the maintainer: refuse unsupported loss scales up front

The ruling (https://github.com/mlakolar/ProximalSolvers.jl/pull/319#issuecomment-6904765782) chose refusal over conversion. Today PS accepts any finite positive `Real` scale whose conversion to `T` is finite and nonzero (subnormal values of `T` included). The new rule, applied in the shared preflight `_check_data` (`src/solve.jl`), reads the scale through `leastsquares_data(f).α` and accepts exactly:

| scale type | accepted when | why it is consistent |
|---|---|---|
| `Float32`, `Float64` | finite, positive, and PS's existing rule in `T` holds (conversion to `T` finite and nonzero; subnormal in `T` allowed) — unchanged | PB uses it as supplied; CD's scale type is the promotion with `T` (a Float64 scale stays Float64 with Float32 data); unchanged behaviour |
| fixed-width integers (`Base.BitInteger`) and `Bool` | positive and `T(α) == α` exactly (which implies `Float64(α) == α`, PB's condition) | CD's `T(α)`, PB's `Float64(α)`, `_lambda_max!` and `_step_curvature` all see the same real number |

Everything else is refused with an `ArgumentError` before any write, in all three solvers: `BigInt` (even when PB would accept its value), `BigFloat`, `Rational`, `Float16`, `Irrational`, any other `Real` type, and fixed-width integers that `T` does not hold (`Int(2^24 + 1)` for Float32 data, `2^53 + 1` for Float64). The message names the type and value and states that only Float32, Float64 and exactly representable fixed-width integer scales are supported. It suggests `Float64(α) * LeastSquaresLoss(y, X)` only when `Float64(α)` is finite, positive and itself passes the rule for `T`; otherwise it carries no suggestion (for example `big(2.0)^2000`, whose Float64 value is `Inf`). The penalty parameter's contract (`_scalar_parameter(g.λ0, …)`) is unchanged.

The check runs in `_check_data`, which `solve!` calls before CD makes its private working iterate and before PGD/APG builds any state from the caller's iterate. Accepted integer scales keep their current code paths (`_root_scale` at 256 bits once per APG solve; CD's scale type `T`).

**This is an intentional narrowing of the PS API**, and the docs and tests say so: `support.md:32-44`, `numerics.md:363-380`, `implementation-notes.md:15,46-50,98-110,129-135`. Tests converted to refusals: `accelerated_pgd.jl:436-470` (BigFloat, Rational, the 256-bit scale, `BigInt(257)`), `cd_numerics.jl:233-254` (BigFloat), `:257-283` (`1//3`, `π`, `Float16(0.3)`), `:1514-1523` (`1//3`, `big"2.0"`, `big(2)//1`), and the solver cases with the `NoPromoScale` type (`cd_numerics.jl:18`). The unit tests of the internal `_scale_type` (`cd_numerics.jl:288-294`) stay, since that function is unchanged. New tests: a table over the accepted and refused types for each `T` (`Int(2^24)` accepted and `Int(2^24 + 1)` refused for Float32; `2^53` and `2^53 + 1` for Float64; `true`; `BigInt(2)`; `UInt8(3)`); refusal before any write for each solver (dense `x` unchanged, `SparseIterate` owner unchanged); the suggestion present or absent as stated; and every accepted scale accepted by the PB oracles.

### Measurements (cluster, Slurm; an exclusive node for every timing; Julia 1.10.13 and 1.13.3; 1 Julia thread, 1 BLAS thread)

Three arms, each a clean detached checkout with its own environment, Manifest receipt **and private depot** (same-UUID checkouts would otherwise share and evict package images):
- **A**: existing PS `637f06a` + old PB `c123d56`;
- **B**: unchanged PS algorithms + PB `50db4b1` (the task-1 commit);
- **C**: migrated PS (the PR head) + the same PB `50db4b1`.

A→B is the dependency-upgrade effect, B→C the migration effect, A→C the overall result. Timings run on an exclusive node (one CPU kind, recorded), with one Julia thread and one BLAS thread, and the CPU, Julia, BLAS and package identities (PS SHA, PB source, revision and tree, Manifest) recorded for every process.

1. **Baseline now** (arm A, authorized): a pilot (one process per measurement kind, both Julia versions) to catch provenance and measurement errors, then first-call latency, precompile/load cost and a formal series, each with an A/A control (two separately built copies of arm A, own environments and depots, interleaved).
2. **First-call latency**: Xoshiro(5) 57×13 Float32/Float64 fixture, `NormL1` at λmax/10 of each loss; **each process measures one (solver, T) pair, so its first solve is the first solver call in a fresh process**; per (solver ∈ CD/PGD/APG, T, order ∈ raw→scaled, scaled→raw), **10 fresh processes per arm and version**, arms interleaved in the final job; compile timing switched on with `Base.cumulative_compile_timing(true)` and read as the first entry of `Base.cumulative_compile_time_ns()`; per solve, wall time and compile time of the first and the immediately repeated call; load and fixture time recorded separately; raw per-process CSV kept; each child checks that the caches it loads are in its arm's private depot. CD's results are reported per (T, loss, order), separately from the aggregate of the six first raw-LS solves.
3. **Precompile and load**: PB and PS precompile wall time (caches removed in the private depot), compiled cache sizes, and `using` load time in fresh processes.
4. **Formal series** (the #318 harness, unchanged): extended suite, groups `cd,gradient` (the current-core cases, the ten `acc-…-f64` among them), `PS_REPETITION=1..10`, arms rotating first per repetition. **B→C** uses the unmodified `compare.py` (identical PB). **A→B and A→C** use a separately labelled cross-dependency wrapper in the run directory: it declares the PB identity keys that may differ (`proximalbase_version`, `proximalbase_hash`, and the PB manifest-entry keys of the start metadata), runs the harness's own `compare.py` code with only those exempted, and refuses any undeclared difference; case IDs, catalog, harness hash, certificate measures and targets, data hashes, Julia threads, BLAS threads and library, and CPU must match. Its report is labelled cross-dependency.
5. **Product counts**: a probe with counting 3-argument `mul!` methods for dense Float32/Float64 `Matrix` and `Transpose{…,Matrix}` times `Vector`, per solve, on fixed problems, in all arms, with the solver counters. No timings come from that process.
6. **Numerical sweep** (run-directory script, rerun on later pushes): values and gradients at the PS call sites against 256-bit references; solver results certified by the independent duality gap or KKT residual. Coverage: Float32/Float64 × raw / scaled / Float32 data with a Float64 scale / integer scale; CD dense and `SparseIterate`, PGD, APG; cold and warm starts; exact and near-exact fits; large n (10⁶ on the value path); zero columns; cancellation; extreme supported scales (subnormal in `T` included); accepted, rejected and restarted backtracking; rollback and refused inputs; R1–R5 of #277; a non-finite predictor (`Xβ` overflows) compared with `f(β)`; the overflowing `z - Y` case of item 2.

### Pre-registered acceptance criteria

- **A1 (scope)**: no PS least-squares value or gradient reduction remains in the migrated paths; they read the loss only through `leastsquares_data` and the three oracles; the byte-identical lists above hold (diff check).
- **A2 (tests)**: on the final head, CI green (every push runs the full tier, since `src/` and `Project.toml` changes select it), docs build green, and the advisory Nightly legs (Julia 1.10 from the Manifest) reported.
- **A3 (accuracy)**: oracle values within PB's documented bound against 256-bit references at every call site in the sweep; every solver case that meets its certificate target in arm A meets it in arms B and C; a case whose certified gap or KKT residual worsens by more than 10× is reported with its cause; the ten `acc-` cases are `ok` in 10/10 repetitions on each Julia version.
- **A4 (work)**: forward and adjoint products per counted evaluation are identical A, B and C; no extra product; iteration, evaluation and backtracking counts reported per case, with differences explained.
- **A5 (allocations and inference)**: 0 warm bytes for `update_state!` (PGD, APG), CD passes, `_stationary!` and `loss_value` on both Julia versions; `@inferred` holds as in task 6; warm `solve!` bytes per formal case not larger than before (a decrease from the `true` → `one(T)` change is reported as such).
- **A6 (time)**: a case is flagged when its median ratio is above 1.05 and its paired 95% interval lies above 1. It is inconclusive when the A/A interval's upper bound is at least the flagged ratio. A flag that persists on a repeat goes to the maintainer with numbers, with arm B showing whether PB's other changes or the migration cause it.
- **A7 (first raw-LS latency)**: for each of the six first raw-LS solves per Julia version and order, the C median is at most the A median × 1.05 or within the A/A spread, whichever is larger (median against median, 10 interleaved processes per arm); CD reported separately, and the six-solve sum too. A→B and B→C separate the dependency and migration effects. The same is reported for scaled LS, with the `true` → `one(T)` effect attributed. On failure, Trial A; if Trial A fails or adds more than 10% to PS precompile time or cache size, the maintainer decides. Without a meaningful regression `precompile.jl` stays unchanged.
- **A8 (precompile and load)**: reported for A, B and C (and after with Trial A, if used); an increase above 10% in load or precompile time goes to the maintainer.
